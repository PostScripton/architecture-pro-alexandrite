# Задание 1. Планирование: анализ, идентификация проблем и поиск решений

Решение находится в файле [Планирование: анализ, идентификация проблем и поиск решений.md](Планирование:%20анализ,%20идентификация%20проблем%20и%20поиск%20решений.md).

## Выявленные проблемы

- Потеря заказов из-за отсутствия dead letter queue и retry в RabbitMQ.
- Отсутствие мониторинга и логирования - невозможно найти, где застрял заказ.
- Медленный дашборд MES: нет индексов, единственный инстанс БД используется и для чтения, и для записи.
- Отсутствие rate limiting на внешнем API: после открытия API компанию завалило заказами, жалоб стало больше.
- Единственные инстансы приложений и БД без реплик - нет отказоустойчивости и масштабируемости.
- Медленный релизный процесс из-за ручного QA на одного инженера.

## Инициативы (11 штук) и приоритизация

Инициативы разбиты на три группы:

- Высокий приоритет: dead letter queue + retry для RabbitMQ, мониторинг очереди и ошибок, rate limiting на API.
- Средний: оптимизация БД MES, структурированное логирование, распределённый трейсинг, read-реплики БД.
- Низкий: горизонтальное масштабирование, асинхронный расчёт стоимости, автотесты, CQRS для MES.

## Целевая архитектура через полгода

Три приложения и RabbitMQ остаются. Добавляется: надёжная доставка сообщений (DLQ + retry), rate limiting, наблюдаемость (метрики, логи, трейсинг), read-реплики БД, оптимизированный дашборд MES. Глубокая переработка архитектуры (CQRS, event sourcing) откладывается - сначала стабилизация.

## Топ-3 инициативы на полгода

1. Dead letter queue и retry для RabbitMQ - устраняет корневую причину потери заказов.
2. Мониторинг очереди и ошибок - без видимости нельзя подтвердить, что проблема решена.
3. Оптимизация запросов и индексов в БД MES - быстрая победа, операторы ежедневно теряют время.
