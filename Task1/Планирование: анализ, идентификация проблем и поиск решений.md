# Планирование: анализ, идентификация проблем и поиск решений

## Идентифицированные проблемы

### Потеря и задержка заказов

- Отсутствует мониторинг очереди RabbitMQ: не видно, где застревают сообщения, есть ли необработанные события, накапливается ли очередь.
- Нет механизма повторной обработки сообщений (retry) и dead letter queue: если обработчик упал или не смог обработать сообщение, оно теряется.
- После открытия внешнего API поток заказов резко вырос - система не имеет защиты от перегрузки (rate limiting, back-pressure), очередь может переполняться.
- Отсутствует сквозной трейсинг заказа: невозможно быстро найти, на каком этапе застрял конкретный заказ.

### Производительность MES

- Страница со списком заказов по статусам работает медленно даже после добавления фильтра и пагинации - скорее всего, отсутствуют нужные индексы в базе данных или запрос не оптимален.
- Единственный инстанс БД используется и для записи, и для чтения: дашборд операторов конкурирует за ресурсы с операциями записи.

### Масштабируемость и отказоустойчивость

- Каждое приложение работает на единственном EC2-инстансе без возможности горизонтального масштабирования.
- Базы данных - одиночные инстансы без реплик. При отказе или пиковой нагрузке вся система встанет.
- Нагрузка растёт линейно (+100 заказов в месяц), но архитектура не готова к дальнейшему росту.

### Расчёт стоимости

- Расчёт стоимости в MES занимает от 2 до 30 минут. Нет явного механизма тайм-аута и нет ясности, что происходит, если процесс расчёта прерывается.
- Нет уведомления клиента о завершении расчёта.

### Процессы доставки и релиза

- Один QA-инженер вручную прогоняет E2E-сценарии - узкое место в релизном процессе.
- Задержки релизов достигают нескольких месяцев. Бизнес не может оперативно получить исправления.

### Наблюдаемость

- Нет инструментов для мониторинга состояния системы (метрики, дашборды), что мешает своевременно обнаруживать проблемы.
- Нет структурированного логирования и агрегации логов - расследование инцидентов занимает много времени.

## Инициативы для устранения проблем

1. Настроить мониторинг и алертинг (метрики приложений, глубина очереди RabbitMQ, ошибки обработки сообщений).
2. Внедрить структурированное логирование и агрегацию логов (например, ELK или аналог).
3. Добавить dead letter queue и retry-механизм для обработки сообщений в RabbitMQ.
4. Ввести rate limiting на внешнем API для защиты от перегрузки.
5. Оптимизировать запросы и индексы в базе данных MES для страницы с заказами.
6. Добавить read-реплики к базам данных для разгрузки операций чтения.
7. Внедрить распределённый трейсинг для сквозного отслеживания заказа по всем сервисам.
8. Реализовать горизонтальное масштабирование для онлайн-магазина и API-шлюза.
9. Перевести расчёт стоимости на асинхронную модель с явным статусом и уведомлением клиента.
10. Запустить автоматизацию регрессионных тестов для ускорения релизного процесса.
11. Добавить возможность масштабирования MES (отделить дашборд операторов от записи через CQRS или реплику для чтения).

## Приоритизация и обоснование

### Порядок приоритетов

**Высокий приоритет (срочно, прямые бизнес-потери):**

1. Dead letter queue и retry для RabbitMQ - заказы теряются прямо сейчас, это приводит к потере контрактов.
2. Мониторинг глубины очереди и ошибок обработки - без видимости невозможно понять масштаб проблемы и убедиться в её устранении.
3. Rate limiting на внешнем API - без ограничения нагрузки система будет деградировать при каждом всплеске.

**Средний приоритет (производительность и стабильность):**

4. Оптимизация запросов и индексов в БД MES - операторы жалуются ежедневно, от этого зависит их вознаграждение.
5. Структурированное логирование и агрегация - ускорит расследование любых инцидентов.
6. Распределённый трейсинг - позволит точно находить, где застрял конкретный заказ.
7. Read-реплики для баз данных - снизит конкуренцию между чтением и записью.

**Низкий приоритет (масштабирование и процессы):**

8. Горизонтальное масштабирование приложений.
9. Асинхронная модель расчёта стоимости с уведомлением клиента.
10. Автоматизация регрессионных тестов.
11. CQRS для MES.

## Целевая архитектура через полгода

Через полгода система должна обеспечить:

- Надёжную доставку сообщений через RabbitMQ: dead letter queue, retry с экспоненциальным отступом, алерты при накоплении необработанных сообщений.
- Rate limiting на внешнем API: защита от перегрузки очереди при всплесках от партнёров.
- Наблюдаемость: метрики (Prometheus + Grafana или аналог), агрегированные логи, базовый distributed tracing - достаточно для оперативного расследования инцидентов.
- Оптимизированный дашборд MES: запросы с индексами, read-реплика для чтения, страница загружается приемлемо быстро.
- Инфраструктура: базы данных имеют как минимум одну read-реплику; приложения способны запускаться в нескольких инстансах (даже если пока работает один).

Архитектура при этом остаётся на трёх приложениях (онлайн-магазин, CRM, MES) с RabbitMQ как шиной между CRM и MES. Глубокая переработка (CQRS, event sourcing) не входит в горизонт полугода - сначала нужно стабилизировать то, что есть.

## Если выбирать только три инициативы

1. **Dead letter queue и retry для RabbitMQ** - устраняет корневую причину потери заказов. Без этого любое другое улучшение не имеет смысла: заказы будут теряться снова при любом сбое обработчика.
2. **Мониторинг очереди и ошибок** - без видимости нельзя подтвердить, что первая инициатива работает, нельзя заранее видеть накопление очереди. Это инструмент контроля, который окупается сразу после внедрения и остаётся навсегда.
3. **Оптимизация запросов и индексов в БД MES** - быстрая победа с большим эффектом: операторы ежедневно теряют время, что влияет на скорость обработки заказов и их вознаграждение. Индексы можно добавить за дни, не меняя архитектуру.

Rate limiting намеренно не попал в тройку: проблему с внешним API можно временно решить административно (ограничить партнёров по квотам договором), пока инфраструктурное решение не готово. Потеря заказов критичнее.
