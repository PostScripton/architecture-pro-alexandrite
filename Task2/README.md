# Задание 2. Мониторинг

Технический документ: `Выбор и настройка мониторинга в системе.md`

## Структура решения

**Мотивация.** Яндекс Метрика не даёт видимости внутри системы. Мониторинг позволяет выявлять проблемы до жалоб клиентов, расследовать инциденты по данным, а не вслепую, и обосновывать решения для бизнеса.

**Подходы к мониторингу:**
- Три API (онлайн-магазин, CRM, MES) - метод RED (Rate, Errors, Duration): подходит для request-driven сервисов.
- Инфраструктура (EC2, базы данных) - метод USE (Utilization, Saturation, Errors): подходит для ресурсов.
- RabbitMQ - USE в адаптированном виде: утилизация - пропускная способность, насыщение - глубина очереди, ошибки - dead-letter-exchange.

**Метрики.** Выбрано 31 метрика, сгруппированных по компонентам:
- RabbitMQ: dead-letter-exchange и in-flight - прямые индикаторы потерянных заказов.
- Shop API: RPS, RPS на пользователя (для rate limiting), latency, HTTP 200/500, CPU, память, сессии.
- CRM API: RPS, latency, HTTP 200/500, CPU, память.
- MES API: RPS, latency, HTTP 200/500, CPU, память.
- БД (shop и MES): память, соединения, размер.
- S3: размер хранилища.
- Дополнительно: время расчёта стоимости в MES и количество заказов по статусу (бизнес-метрика).

Для каждой метрики описано обоснование и ярлыки (labels).

**Насыщенность.** Определены пороговые значения для RabbitMQ (>1000 in-flight), БД (>80% соединений), CPU (>80% в течение 5 минут), памяти (>85%) с описанием действий при превышении.

**План действий:** развернуть Prometheus + Grafana, подключить Prometheus-клиенты к Java Spring Boot и C#-приложениям, настроить экспортеры RabbitMQ и баз данных Yandex Cloud, создать дашборды, настроить Alertmanager.
