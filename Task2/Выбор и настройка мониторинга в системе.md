# Выбор и настройка мониторинга в системе

## Мотивация

Яндекс Метрика отслеживает поведение посетителей сайта, но не даёт картины того, что происходит внутри системы. После открытия внешнего API и роста числа заказов возникли проблемы, которые Метрика не видит: сообщения теряются в RabbitMQ, дашборд операторов MES работает медленно, конкретный заказ невозможно отследить по всем сервисам.

Без мониторинга инфраструктуры команда узнаёт о проблемах только от клиентов - уже после того, как потери произошли. Мониторинг даст следующее:

- Раннее обнаружение: проблема видна до того, как клиент пожалуется.
- Данные для расследования: вместо слепого поиска в логах - конкретные метрики с временными метками.
- Понимание тенденций: нагрузка растёт на 100 заказов в месяц, мониторинг покажет, когда ресурсы начнут заканчиваться.
- Обоснование для бизнеса: метрики позволяют доказать, что проблема решена, или показать, что ресурсов недостаточно.

---

## Выбор подхода к мониторингу

Система состоит из трёх типов компонентов, для каждого выбран отдельный подход.

**Три API (онлайн-магазин, CRM, MES) - метод RED:**
- Rate - количество запросов в секунду.
- Errors - количество ошибок.
- Duration - время ответа.

RED разработан специально для request-driven сервисов. Все три API принимают HTTP-запросы, поэтому RED подходит наиболее точно. Он позволяет ответить на главные вопросы: система справляется с нагрузкой? сколько запросов завершается ошибкой? как быстро отвечает?

**Инфраструктура (EC2-инстансы, базы данных) - метод USE:**
- Utilization - насколько ресурс занят (CPU %, RAM %).
- Saturation - насколько ресурс перегружен (очередь запросов, ожидание).
- Errors - ошибки на уровне ресурса.

USE предназначен для ресурсов, а не для запросов. Базы данных и EC2-инстансы - ресурсы, поэтому USE логичен.

**RabbitMQ - USE (адаптированный):**
Очередь - это ресурс. Утилизация - пропускная способность, насыщение - глубина очереди, ошибки - письма в dead-letter-exchange.

## Метрики

### RabbitMQ

**1. Количество сообщений в dead-letter-exchange**

- Зачем: прямой индикатор потерянных или необработанных сообщений. Любое значение больше нуля означает, что заказ завис или потерян.
- Ярлыки: `queue_name` (чтобы разделять разные очереди между CRM и MES).

**2. Количество сообщений in-flight**

- Зачем: показывает накопление очереди. Если значение растёт, MES или CRM не успевают обрабатывать сообщения.
- Ярлыки: `queue_name`.

---

### Онлайн-магазин API

**3. Количество запросов (RPS)**

- Зачем: базовая метрика нагрузки. Важна для понимания пиков - особенно после открытия внешнего API.
- Ярлыки: `endpoint`, `http_method`.

**4. Количество запросов (RPS) на пользователя**

- Зачем: позволяет выявить аномально высокую нагрузку от одного клиента или партнёра и ввести rate limiting.
- Ярлыки: `client_id` (для B2B-партнёров), `endpoint`.

**5. Время ответа (latency)**

- Зачем: метрика Duration в RED. Деградация времени ответа - первый признак проблемы ещё до роста ошибок.
- Ярлыки: `endpoint`, `http_method`, `status_code`.

**6. Количество HTTP 200**

- Зачем: подтверждает, что запросы обрабатываются успешно. Полезно в паре с RPS для вычисления доли успешных запросов.
- Ярлыки: `endpoint`, `http_method`.

**7. Количество HTTP 500**

- Зачем: метрика Errors в RED. Рост серверных ошибок - прямой сигнал проблемы в приложении.
- Ярлыки: `endpoint`, `http_method`.

**8. CPU %**

- Зачем: метрика Utilization в USE. Высокая загрузка CPU при единственном инстансе означает деградацию или необходимость масштабирования.
- Ярлыки: нет (один инстанс).

**9. Потребление памяти**

- Зачем: метрика Utilization в USE. Memory leak или резкий рост потребления видны заранее.
- Ярлыки: нет.

**10. Число одновременных сессий**

- Зачем: показывает реальную нагрузку на уровне соединений. Важно для B2C: всплеск сессий может предшествовать деградации.
- Ярлыки: нет.

---

### CRM API

**11. Количество запросов (RPS)**

- Зачем: CRM принимает запросы от продавцов и сообщения из RabbitMQ. Рост RPS при открытии API партнёрам сразу виден.
- Ярлыки: `endpoint`, `http_method`.

**12. Время ответа (latency)**

- Зачем: продавцы работают в CRM ежедневно. Деградация времени ответа напрямую влияет на их продуктивность.
- Ярлыки: `endpoint`, `http_method`, `status_code`.

**13. Количество HTTP 200**

- Зачем: базовый индикатор успешности. Используется для расчёта error rate.
- Ярлыки: `endpoint`, `http_method`.

**14. Количество HTTP 500**

- Зачем: серверные ошибки в CRM могут означать, что заказы не создаются или не обновляются.
- Ярлыки: `endpoint`, `http_method`.

**15. CPU %**

- Зачем: USE для EC2-инстанса CRM.
- Ярлыки: нет.

**16. Потребление памяти**

- Зачем: USE для EC2-инстанса CRM.
- Ярлыки: нет.

---

### MES API

**17. Количество запросов (RPS)**

- Зачем: операторы и внешние партнёры используют MES. Рост RPS помогает соотнести нагрузку с жалобами на медленный дашборд.
- Ярлыки: `endpoint`, `http_method`.

**18. Время ответа (latency)**

- Зачем: самая важная метрика для MES. Дашборд операторов тормозит - latency по эндпоинту списка заказов покажет реальную картину. Также важна для эндпоинта расчёта стоимости (2-30 минут).
- Ярлыки: `endpoint`, `http_method`, `status_code`.

**19. Количество HTTP 200**

- Зачем: для расчёта доли успешных запросов.
- Ярлыки: `endpoint`, `http_method`.

**20. Количество HTTP 500**

- Зачем: ошибки MES могут означать сбой расчёта стоимости или проблему с базой данных.
- Ярлыки: `endpoint`, `http_method`.

**21. CPU %**

- Зачем: расчёт стоимости (особенно сложных моделей) нагружает CPU. Метрика покажет, когда одного инстанса не хватает.
- Ярлыки: нет.

**22. Потребление памяти**

- Зачем: расчёт стоимости детализированных 3D-моделей может требовать значительного объёма памяти.
- Ярлыки: нет.

---

### Базы данных

**23. Потребление памяти - shop DB**

- Зачем: managed DB в Yandex Cloud имеет ограниченные ресурсы. Рост потребления памяти предупреждает о необходимости апгрейда.
- Ярлыки: нет.

**24. Потребление памяти - MES DB**

- Зачем: то же самое. MES DB хранит данные по всем заказам, размер растёт линейно.
- Ярлыки: нет.

**25. Число соединений - shop DB**

- Зачем: при единственном инстансе без реплик пул соединений - узкое место. Достижение лимита приведёт к ошибкам приложения.
- Ярлыки: нет.

**26. Число соединений - MES DB**

- Зачем: дашборд операторов и API расчёта стоимости конкурируют за соединения с одной БД. Метрика покажет момент насыщения.
- Ярлыки: нет.

**27. Размер shop DB**

- Зачем: планирование ёмкости. При линейном росте заказов размер БД растёт предсказуемо.
- Ярлыки: нет.

**28. Размер MES DB**

- Зачем: то же самое.
- Ярлыки: нет.

---

### S3

**29. Размер S3-хранилища**

- Зачем: S3 хранит 3D-модели пользователей. Каждый заказ добавляет как минимум один файл. Метрика нужна для планирования затрат.
- Ярлыки: нет.

## Дополнительные метрики (не в исходном списке)

**30. Время расчёта стоимости в MES**

- Зачем: расчёт занимает от 2 до 30 минут. Нужна отдельная метрика, чтобы видеть распределение времени обработки и выявлять аномально долгие расчёты.
- Ярлыки: нет (детализация по конкретному заказу - уже задача трейсинга).

**31. Количество заказов по статусу**

- Зачем: бизнес-метрика. Позволяет видеть, сколько заказов застряло на каждом этапе жизненного цикла - прямое отражение проблем, о которых жалуются клиенты.
- Ярлыки: `status` (INITIATED, FILE_UPLOADED, SUBMITTED и т.д.).

## Насыщенность (дополнительное задание)

Насыщение - это состояние, когда ресурс работает на пределе и дальнейший рост нагрузки приведёт к деградации.

**RabbitMQ - глубина очереди**

- Пороговое значение: более 1000 сообщений in-flight в одной очереди.
- Обоснование: при линейном росте в 100 заказов в месяц нормальная глубина очереди в спокойный период - единицы. Накопление до 1000 означает, что потребитель не справляется.
- Действие: алерт в мессенджер команды, ручная проверка потребителей, при повторении - масштабирование инстанса MES или CRM.

**Базы данных - число соединений**

- Пороговое значение: 80% от максимального числа соединений managed DB-инстанса.
- Обоснование: при достижении 100% новые запросы начнут падать с ошибкой. Порог 80% даёт время на реакцию.
- Действие: алерт в мессенджер команды. Краткосрочно - ограничить пул соединений в приложении. Среднесрочно - добавить read-реплику и перевести на неё запросы на чтение.

**CPU EC2-инстансов**

- Пороговое значение: CPU > 80% в течение 5 минут подряд.
- Обоснование: кратковременные пики нормальны. Устойчивый высокий CPU означает, что инстанс перегружен.
- Действие: алерт в мессенджер команды. Для MES - проверить, не застрял ли расчёт стоимости сложной модели. При систематическом превышении - апгрейд EC2 или горизонтальное масштабирование.

**Память EC2-инстансов**

- Пороговое значение: RAM > 85%.
- Обоснование: при нехватке памяти JVM (Java Spring Boot) начинает активно собирать мусор, что приводит к latency spikes. C# ведёт себя аналогично.
- Действие: алерт, расследование утечки памяти или апгрейд инстанса.

## План действий

1. Развернуть Prometheus как time-series базу данных для хранения метрик. Использовать managed-решение или EC2-инстанс в Yandex Cloud.
2. Развернуть Grafana для визуализации метрик и создания дашбордов.
3. Подключить Prometheus-клиенты к приложениям:
   - Java Spring Boot (онлайн-магазин, CRM) - добавить Spring Boot Actuator с Micrometer и Prometheus-экспортером.
   - C# (MES) - добавить библиотеку prometheus-net.
4. Настроить RabbitMQ-экспортер для Prometheus (rabbitmq_exporter) для метрик очередей.
5. Настроить экспортеры для баз данных Yandex Cloud (Managed PostgreSQL отдаёт метрики в Yandex Monitoring; настроить интеграцию с Prometheus через Yandex Monitoring API или отдельный экспортер).
6. Настроить экспортер для S3-хранилища (Yandex Object Storage Exporter или Yandex Monitoring).
7. Создать дашборды в Grafana:
   - Обзорный дашборд системы (все три API, RabbitMQ, БД).
   - Дашборд очереди заказов по статусам.
   - Дашборд производительности MES (latency дашборда операторов, время расчёта стоимости).
8. Настроить Alertmanager и правила алертов для пороговых значений насыщенности.
9. Провести нагрузочное тестирование для проверки алертов и дашбордов под нагрузкой.
