# Архитектурное решение по трейсингу

## Анализ системы

### Системы, которые следует покрыть трейсингом

На схеме системы (C4 Container Diagram) заказ проходит через следующие компоненты, которые нужно инструментировать:

- **Shop API** (Java Spring Boot) - принимает заказ от покупателя, сохраняет в Shop DB, загружает 3D-файл в S3, публикует сообщение в RabbitMQ о смене статуса.
- **CRM API** (Java Spring Boot) - получает сообщения из RabbitMQ, подтверждает заказ (MANUFACTURING_APPROVED), публикует сообщение обратно в очередь.
- **MES API** (C#) - получает сообщения из RabbitMQ, рассчитывает стоимость (от 2 до 30 минут), управляет статусами заказа, взаимодействует с S3 и MES DB.
- **RabbitMQ** - шина сообщений между сервисами. Ключевое место потери заказов: сообщение может попасть в dead-letter очередь, и никто об этом не узнает.

Фронтенды (Internet Shop, CRM, MES) в трейсинг не включаем - они не участвуют в серверной логике обработки заказа.

### Места, где заказ может сломаться или зависнуть

- Shop API не опубликовал сообщение в RabbitMQ после перехода в статус SUBMITTED - заказ зависает навсегда.
- Сообщение попало в dead-letter очередь RabbitMQ - заказ не дошёл до CRM или MES.
- MES API завис на расчёте стоимости - задача может занимать до 30 минут, но неизвестно, идёт ли расчёт или сервис упал.
- CRM API не подтвердил заказ (нет MANUFACTURING_APPROVED) - заказ остался в PRICE_CALCULATED без движения.
- Ошибка записи в БД без rollback сообщения в очереди - несогласованность данных между Shop DB и MES DB.

### Данные, которые должны попадать в трейсинг

- `order_id` - обязательный атрибут каждого спана (через baggage или явный атрибут)
- `trace_id`, `span_id`, `parent_span_id` - стандартные поля трейса
- `service.name` - имя сервиса
- `operation_name` - название операции (например, `order.submit`, `price.calculate`, `message.publish`)
- `timestamp`, `duration` - время начала и длительность
- `order.status_before`, `order.status_after` - переходы статусов
- `http.method`, `http.url`, `http.status_code` - для HTTP-вызовов
- `messaging.system` = `rabbitmq`, `messaging.destination`, `messaging.message_id` - для сообщений в очереди
- `db.system`, `db.operation` - для запросов в БД
- `error` (boolean), `error.type`, `error.message` - при ошибке

## Мотивация

Сейчас при проблемах с заказом команда не знает, на каком шаге заказ завис или был потерян. Расследование требует ручного разбора логов из трёх систем, которые не связаны между собой единым идентификатором.

Трейсинг позволяет отследить путь заказа сквозь все системы по единому `order_id` и `trace_id`, увидеть точку сбоя и длительность каждого шага.

**Технические и бизнес-метрики, на которые повлияет внедрение трейсинга:**

- **MTTR (Mean Time To Resolve)** - сейчас расследование инцидента требует часов ручного анализа логов. С трейсингом точка сбоя находится за минуты.
- **Количество необнаруженных потерянных заказов** - трейсинг позволяет обнаружить заказы, застрявшие в очереди или на расчёте стоимости, до жалоб клиентов.
- **P95 latency расчёта стоимости (MES API)** - сейчас нет видимости по распределению времени расчёта; трейсинг позволит выявить аномально долгие операции и их причины.
- **Процент заказов с нарушением SLA** - зная, на каком этапе теряется время, можно контролировать выполнение обязательств перед клиентами (обещанные 3 недели).
- **Количество сообщений в dead-letter очереди** - в связке с трейсингом можно понять, какой тип сообщений теряется и почему (без трейсинга это только число без контекста).

## Предлагаемое решение

### Стек

- **OpenTelemetry SDK** - стандарт инструментирования сервисов. Для Java (Shop API, CRM API) - `opentelemetry-java-instrumentation` в режиме java-agent (минимум изменений в коде). Для C# (MES API) - пакеты `OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Instrumentation.AspNetCore`, `OpenTelemetry.Instrumentation.Http`, `OpenTelemetry.Instrumentation.EntityFrameworkCore`.
- **OpenTelemetry Collector** - центральный агрегатор трейсов. Принимает данные от сервисов по OTLP gRPC, форвардит в Jaeger. Позволяет менять бэкенд трейсинга без изменений в сервисах.
- **Jaeger** - хранение и визуализация трейсов. Развёртывается в режиме all-in-one для dev/release, с Elasticsearch-бэкендом для prod.

### Пропагация контекста в RabbitMQ

Стандартные HTTP-заголовки (W3C TraceContext) не работают для очередей из коробки. При публикации сообщения в RabbitMQ нужно записывать `traceparent` и `tracestate` в заголовки AMQP-сообщения, при получении - извлекать их и создавать новый спан с этим родительским контекстом. Для Java это делается через `opentelemetry-instrumentation-rabbitmq`; для C# - вручную через `TextMapPropagator`.

### Что нужно доработать

- Shop API, CRM API: подключить java-agent через переменную окружения `JAVA_TOOL_OPTIONS`. Для базового трейсинга HTTP и БД изменений в коде не требуется. Для RabbitMQ и атрибута `order_id` - минимальные правки в consumer/producer.
- MES API: добавить NuGet-пакеты OpenTelemetry. Для RabbitMQ и атрибута `order_id` - ручное добавление спанов.
- Развернуть OpenTelemetry Collector как отдельный сервис (один инстанс на среду).
- Развернуть Jaeger (all-in-one для dev/release, с persistence-бэкендом для prod).

### Мониторинг и алертинг на основе трейсинга (дополнительное задание)

Jaeger предоставляет метрики производительности сервисов (Service Performance Monitoring, SPM) в формате Prometheus. Grafana подключается к этим метрикам и к Jaeger как источникам данных.

**Алерты на основе данных трейсинга:**

- Заказ не перешёл из SUBMITTED в PRICE_CALCULATED за 35 минут - сигнал о потере сообщения в очереди или зависании MES API.
- P95 длительности спана `price.calculate` > 30 минут - аномально долгий расчёт.
- Спан `message.publish` завершился с `error=true` - ошибка публикации в RabbitMQ.
- Доля спанов с ошибкой по сервису > 5% за последние 5 минут - деградация сервиса.

Алерты из Grafana направляются в Alertmanager, который маршрутизирует уведомления в Slack (команда разработки) и PagerDuty (дежурный инженер при critical-уровне).

## Компромиссы

- **MES - купленная система с исходным кодом**: внедрение OTel SDK возможно, но требует модификации купленного кода. При обновлении MES от вендора изменения придётся накладывать повторно. Стоимость - несколько дней работы C#-разработчика.
- **RabbitMQ**: библиотека `opentelemetry-instrumentation-rabbitmq` для Java находится в стадии alpha. Пропагация контекста через AMQP-заголовки требует явного кода в consumer/producer - не полностью автоматическая.
- **Трейсинг не поможет при инфраструктурных сбоях**: падение EC2-инстанса, сетевые разрывы между сервисами - трейсы просто не будут создаваться или будут неполными.
- **Overhead при высокой нагрузке**: каждый запрос создаёт спан с метаданными. Решение - sampling (10% для prod при штатной работе, 100% при инцидентах через динамическую конфигурацию OTel Collector).
- **S3 (Yandex Cloud)**: Managed-сервис. OTel SDK умеет инструментировать AWS S3 SDK, но Yandex Cloud S3 совместим с AWS API, поэтому инструментирование может работать частично или потребовать доработки.

## Безопасность

- **Доступ к Jaeger UI** - Jaeger развёртывается без публичного expose. Доступ только через VPN или ingress с аутентификацией (OAuth2 proxy + корпоративный SSO). Роли: "поддержка" и "разработчик" могут просматривать трейсы, остальные - нет.
- **Данные в трейсах** - запрещено записывать персональные данные клиентов (имя, адрес, контакты) в атрибуты спанов. В трейсах хранятся только технические идентификаторы: `order_id`, `user_id` (внутренний), статусы. Требование фиксируется в технических гайдлайнах команды.
- **Транспорт** - OTLP-трафик от сервисов до OTel Collector передаётся по TLS (mTLS для prod). Collector и Jaeger находятся в закрытом сегменте сети, недоступном снаружи.
- **Ротация данных** - трейсы хранятся не более 7 дней (Jaeger TTL), что снижает риск накопления чувствительных технических данных.
