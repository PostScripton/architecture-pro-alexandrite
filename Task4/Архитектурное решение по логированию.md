# Архитектурное решение по логированию

## Анализ системы

### Системы, которые требуют сбора логов

На схеме системы (C4 Container Diagram) обработка заказа проходит через следующие компоненты, из которых необходимо собирать логи:

- **Shop API** (Java Spring Boot) - принимает заказ от покупателя, загружает 3D-файл в S3, публикует сообщения в RabbitMQ об изменении статусов.
- **CRM API** (Java Spring Boot) - получает сообщения из RabbitMQ, подтверждает заказ (MANUFACTURING_APPROVED), закрывает заказ (CLOSED).
- **MES API** (C#) - получает сообщения из RabbitMQ, рассчитывает стоимость (от 2 до 30 минут), управляет переходами статусов заказа.
- **RabbitMQ** - шина сообщений между сервисами. Критическое место: сообщение может попасть в dead-letter очередь без уведомления.

Фронтенды (Internet Shop, CRM, MES) в сбор логов не включаем на первом этапе - они не содержат бизнес-логики обработки заказа и их ошибки видны напрямую пользователям.

### Необходимые логи с уровнем INFO

**Shop API**:
- Создание заказа: `order_id`, `user_id`, `timestamp`
- Загрузка 3D-файла: `order_id`, `file_name`, `file_size_bytes`, `duration_ms`
- Переход статуса заказа: `order_id`, `status_from`, `status_to`, `timestamp`
- Публикация сообщения в RabbitMQ: `order_id`, `queue_name`, `message_id`, `timestamp`
- Входящий HTTP-запрос: `method`, `path`, `http_status`, `duration_ms`, `user_id`

**CRM API**:
- Получение сообщения из RabbitMQ: `order_id`, `queue_name`, `message_id`, `timestamp`
- Переход статуса заказа: `order_id`, `status_from`, `status_to`, `seller_id`, `timestamp`
- Входящий HTTP-запрос: `method`, `path`, `http_status`, `duration_ms`, `user_id`

**MES API**:
- Получение сообщения из RabbitMQ: `order_id`, `queue_name`, `message_id`, `timestamp`
- Начало расчёта стоимости: `order_id`, `file_size_bytes`, `timestamp`
- Завершение расчёта стоимости: `order_id`, `calculated_price`, `duration_ms`, `timestamp`
- Переход статуса заказа: `order_id`, `status_from`, `status_to`, `operator_id`, `timestamp`
- Входящий HTTP-запрос: `method`, `path`, `http_status`, `duration_ms`, `user_id`

**RabbitMQ**:
- Успешная доставка сообщения: `queue_name`, `message_id`, `routing_key`, `timestamp`
- Подтверждение сообщения (ack): `queue_name`, `message_id`, `timestamp`

### Другие уровни логирования

**DEBUG** - детали внутренней логики: параметры запросов к БД, тело сообщений RabbitMQ, промежуточные шаги расчёта стоимости. Включается только в dev- и release-окружениях. В prod отключён для снижения объёма хранилища.

**WARN** - неожиданные, но не критичные ситуации:
- Повторная попытка публикации сообщения в RabbitMQ.
- Медленный запрос к БД (> 500 мс).
- Расчёт стоимости занял более 20 минут (приближается к порогу).
- Сообщение попало в dead-letter очередь.

**ERROR** - ошибки, требующие вмешательства:
- Неудачная публикация сообщения в RabbitMQ после всех повторных попыток.
- Исключение при обработке сообщения из очереди.
- Недоступность базы данных.
- Ошибка загрузки файла в S3.
- Любое непредвиденное исключение при обработке HTTP-запроса (5xx).

**FATAL** - критические сбои, приводящие к остановке сервиса: невозможность подключиться к RabbitMQ при старте, ошибка инициализации приложения.

### Приоритет внедрения

Команда не может внедрить логирование всех систем одновременно. Приоритет:

1. **CRM API + MES API + RabbitMQ** - именно в этой части происходят потери заказов. Большинство жалоб связано с тем, что заказ зависает где-то между PRICE_CALCULATED и MANUFACTURING_APPROVED. Логи этих трёх компонентов дадут ответ на вопрос "где заказ?" в большинстве случаев.
2. **Shop API** - входная точка. Нужен для подтверждения, что заказ вообще был принят и сообщение было опубликовано в очередь.
3. **Фронтенды** - на последнем месте, так как ошибки там видны пользователям напрямую, и они не связаны с потерями заказов в производстве.

## Мотивация

Сейчас разбор проблем с заказами ведётся со слов клиентов. Команда не знает, на каком шаге заказ завис, и вынуждена вручную опрашивать три независимые системы - Shop, CRM и MES - без общего идентификатора для поиска. Это занимает часы и требует участия разработчиков.

Централизованное логирование решает эту проблему: все события по заказу собираются в одном месте и доступны по `order_id` за секунды.

**Метрики, на которые повлияет внедрение:**

- **MTTR (среднее время устранения инцидента)** - сейчас расследование одного случая потери заказа требует участия нескольких разработчиков и занимает несколько часов. Централизованные логи с поиском по `order_id` позволят найти место сбоя за минуты.
- **Процент необнаруженных потерянных заказов** - сейчас компания узнаёт о потерях только от клиентов. Логи позволят обнаруживать зависшие заказы проактивно, до жалобы.
- **Нагрузка на службу поддержки** - количество обращений, по которым поддержка не может дать ответ без подключения разработчика, снизится, так как поддержка сможет самостоятельно проверить статус заказа по логам.
- **P95 времени расчёта стоимости (MES API)** - сейчас нет видимости по распределению времени расчёта. Логи позволят отслеживать медианное и хвостовое время, выявлять аномально долгие расчёты и их причины.
- **Количество инцидентов с потерей контрактов** - после внедрения логирования команда сможет реагировать на проблемы с B2B-заказами до того, как клиент обнаружит нарушение.

## Предлагаемое решение

### Стек

- **Fluent Bit** - лёгкий агент сбора логов. Запускается на каждом EC2-инстансе, читает stdout всех приложений, добавляет метаданные (`hostname`, `environment`, `service_name`, `version`), пересылает в Logstash.
- **Logstash** - обработчик и маршрутизатор логов. Парсит JSON-формат, маскирует поля с чувствительными данными, маршрутизирует по отдельным индексам (один индекс на сервис + окружение).
- **OpenSearch** - хранилище и поисковый движок. Используется Managed OpenSearch в Yandex Cloud - это снимает операционную нагрузку с единственного DevOps-инженера.
- **OpenSearch Dashboards** - веб-интерфейс для поиска логов, построения дашбордов и настройки алертов.

Сервисы пишут логи в stdout в структурированном JSON-формате. Для Java (Shop API, CRM API) - через библиотеку `logstash-logback-encoder`. Для C# (MES API) - через `Serilog` с `Serilog.Sinks.Console` в формате JSON.

### Политика безопасности

**Чувствительные данные:**
- В логах запрещено хранить персональные данные клиентов: имя, адрес доставки, email, номер телефона, платёжные данные.
- Допускаются только технические идентификаторы: `order_id`, `user_id` (внутренний UUID), `operator_id`, `seller_id`.
- Logstash маскирует потенциально чувствительные поля через `mutate { gsub }` или `ruby` filter, если они случайно попали в лог (например, тело запроса с email).
- Требование фиксируется в технических гайдлайнах команды и добавляется в шаблон кодревью.

**Доступ к логам:**
- OpenSearch Dashboards доступен только через VPN + корпоративный SSO.
- Роли:
  - `developer` - чтение логов своих сервисов в любом окружении.
  - `devops` - полный доступ ко всем индексам и настройкам.
  - `support` - чтение prod-логов на уровне INFO и выше (без DEBUG).
  - Прямой доступ к API OpenSearch для внешних пользователей закрыт.
- Logstash и OpenSearch находятся в закрытом сегменте сети Yandex Cloud VPC, недоступном из интернета.

### Политика хранения

Для каждого сервиса создаётся отдельный индекс:
- `logs-shop-api-{env}-{YYYY.MM.dd}`
- `logs-crm-api-{env}-{YYYY.MM.dd}`
- `logs-mes-api-{env}-{YYYY.MM.dd}`
- `logs-rabbitmq-{env}-{YYYY.MM.dd}`

Сроки хранения по уровню (через Index Lifecycle Management):

- ERROR и выше: 90 дней в hot-tier, затем удаление.
- INFO: 30 дней.
- DEBUG: 7 дней (только dev и release окружения; в prod DEBUG не включён).

Ожидаемый объём: при текущей нагрузке (несколько сотен заказов в месяц) объём INFO-логов за 30 дней составит менее 10 ГБ. Managed OpenSearch в Yandex Cloud поддерживает горизонтальное масштабирование при росте нагрузки.

## Превращение системы сбора логов в систему анализа логов

### Алертинг

OpenSearch Alerting (встроенный инструмент) позволяет настраивать алерты напрямую без дополнительных компонентов. Оповещения направляются в Slack (команда разработки) и на email (дежурный).

Необходимые алерты:

- **Заказ завис в SUBMITTED > 5 минут** - не пришло сообщение о PRICE_CALCULATED. Сигнал: сообщение не дошло до MES API или MES API не принял его.
- **Заказ завис в PRICE_CALCULATED > 35 минут** - расчёт не завершился в разумный срок. Возможные причины: MES API завис, зависание процесса расчёта.
- **Сообщение попало в dead-letter очередь** - любое сообщение с `level: WARN` и маркером `dead-letter` в RabbitMQ-логах.
- **Количество ERROR в любом сервисе > 10 за 5 минут** - признак деградации сервиса.
- **Нет логов от сервиса > 2 минут** (отсутствие heartbeat) - сервис недоступен или упал.

### Обнаружение аномалий

Аномалии, которые нужно отслеживать:

- **Резкий рост числа создаваемых заказов** - если за 1 минуту количество событий `INITIATED` превысило среднее значение за последние 24 часа в 10 раз и более, это может быть DDoS-атака или злоупотребление API.
- **Массовые ошибки одного типа** - если за 5 минут в логах доминирует один класс исключений (например, `ConnectionRefusedException` к БД), это признак инфраструктурного сбоя, а не случайной ошибки.
- **Аномально долгий расчёт стоимости** - если P95 `duration_ms` для события завершения расчёта превысил исторический максимум, это сигнал о деградации MES API или проблеме с конкретным файлом.
- **Рост очереди без обработки** - если количество входящих сообщений в RabbitMQ не уменьшается в течение нескольких минут, потребители зависли.

На первом этапе аномалии обнаруживаются вручную через дашборды OpenSearch. При наличии исторических данных (3+ месяцев) можно настроить автоматические алерты на основе z-score средних значений в OpenSearch Alerting.

## Дополнительное задание. Выбор технологии для работы с логами

### Критерии выбора

**ELK Stack** (Elasticsearch + Logstash + Kibana) - технологический лидер рынка, но сменил лицензию на SSPL (не совместима с коммерческим использованием без покупки лицензии Elastic).

**OpenSearch** - форк Elasticsearch под лицензией Apache 2.0, созданный AWS после изменения лицензии. Функционально эквивалентен ELK.

**Splunk** - проприетарная корпоративная платформа. Лидер по функциональности для анализа аномалий и Security Analytics.

**Grafana Loki** - лёгкое решение без полнотекстовой индексации (хранит только метки + сырые строки). Дешевле по хранилищу, но беднее по возможностям поиска.

- Лицензия
  - ELK: Elastic License 2.0 (SSPL) - ограничения на коммерческое SaaS-использование
  - OpenSearch: Apache License 2.0 - без ограничений
  - Splunk: проприетарная
  - Loki: Apache License 2.0 - без ограничений

- Стоимость (TCO для команды из 9 человек)
  - ELK: self-hosted бесплатно, Elastic Cloud от $16/мес. Лицензионные риски при commercial use
  - OpenSearch: self-hosted бесплатно, Managed в Yandex Cloud - оплата за ресурсы (~$100-300/мес при умеренной нагрузке)
  - Splunk: от $150/ГБ/день в проприетарной лицензии - недоступно для небольшой компании
  - Loki: self-hosted бесплатно, Grafana Cloud есть free tier; дешевле из-за отсутствия полного индекса

- Наличие Managed Service в Yandex Cloud
  - ELK: нет официального managed
  - OpenSearch: есть Managed OpenSearch в Yandex Cloud - ключевое преимущество для команды с одним DevOps
  - Splunk: нет
  - Loki: нет, нужно развёртывать самостоятельно

- Богатство языка запросов
  - ELK: Elasticsearch Query DSL + KQL в Kibana - мощный полнотекстовый поиск
  - OpenSearch: то же самое (форк) - PPL и SQL поверх Query DSL
  - Splunk: SPL (Search Processing Language) - наиболее мощный, но требует обучения
  - Loki: LogQL - поиск только по меткам и паттернам в тексте, без агрегаций по произвольным полям

- Полнотекстовая индексация и агрегации
  - ELK: полная индексация всех полей, агрегации любой сложности
  - OpenSearch: то же самое
  - Splunk: то же самое + ML-аномалии из коробки
  - Loki: нет полного индекса - поиск по паттернам в тексте медленнее, агрегации ограничены

- Алертинг из коробки
  - ELK: Watcher (платный) или через Grafana
  - OpenSearch: OpenSearch Alerting - встроен, бесплатен, поддерживает destinations (Slack, email, webhook)
  - Splunk: встроен, богатые возможности
  - Loki: через Grafana Alerting (общий стек)

- Операционная сложность для команды
  - ELK: требует настройки ILM, security, шардирования - высокая нагрузка на DevOps
  - OpenSearch: аналогично ELK, но Managed в Yandex Cloud снимает большую часть нагрузки
  - Splunk: SaaS - минимальная операционная нагрузка, но цена запретительна
  - Loki: проще в операционном плане, хорошо интегрируется с Grafana, которая уже может быть в стеке

### Решение

Выбор - **OpenSearch (Managed в Yandex Cloud)**.

Ключевые причины:
- Единственный вариант с Managed Service в Yandex Cloud, что критично при одном DevOps-инженере в команде.
- Лицензия Apache 2.0 - нет юридических рисков, в отличие от ELK.
- Функционально эквивалентен ELK: полный поиск по всем полям, агрегации, встроенный алертинг.
- Поисковые возможности значительно лучше, чем у Loki, - нужны агрегации по `order_id`, `status`, `duration_ms`.
- Цена приемлема для текущего объёма данных.

Splunk отклонён из-за стоимости. Loki отклонён из-за ограниченных возможностей полнотекстового поиска, которые нужны для анализа бизнес-событий заказов.
