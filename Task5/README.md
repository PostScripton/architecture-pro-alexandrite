## Архитектурное решение (задание 5)

**Проблема:** медленная загрузка первой страницы MES - списка заказов по статусам. При каждом обновлении страницы MES API делает тяжелый запрос к единственному инстансу MES DB. При одновременной работе нескольких операторов, конкурирующих за новые заказы, нагрузка на БД растёт.

**Что кешируем:** результаты GET /orders?status=X&page=N - страницы списка заказов по статусам.

**Тип кеширования:** серверное (Redis на стороне MES API). Клиентское (браузерный кеш) не подходит: кеш per-operator не снижает нагрузку на БД при N одновременных операторах, и инвалидация не работает между браузерами - двое могут взять один заказ.

**Паттерн:** Cache-Aside. MES API проверяет Redis перед обращением к БД; при промахе - загружает из БД и сохраняет в Redis. Write-Through отклонён (добавляет latency на запись, избыточно при редких записях). Refresh-Ahead отклонён (нет предсказуемых паттернов доступа).

**Инвалидация:** программная по ключу (немедленное удаление `orders:status:{old_status}:*` и `orders:status:{new_status}:*` при изменении статуса) + TTL=60s как страховка от бессрочного устаревания при сбое инвалидации.

**Технология:** Redis (Managed в Yandex Cloud). Интеграция через StackExchange.Redis для C# (MES API).
