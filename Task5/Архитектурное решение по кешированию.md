# Архитектурное решение по кешированию

## Анализ системы

Главная жалоба операторов - медленная загрузка первой страницы MES. Эта страница показывает список заказов в работе по статусам (дашборд с фильтром и пагинацией). При каждом открытии или обновлении страницы MES API делает запрос к MES DB - единственному инстансу PostgreSQL, который работает и на запись, и на чтение. При росте числа заказов и числа операторов, которые обновляют страницу в поиске новых заказов, этот запрос становится источником проблемы.

Список заказов по статусам - это данные с высоким соотношением чтений к записям: операторы обновляют страницу постоянно, а статус заказа меняется значительно реже. Это классический кандидат для кеширования.

## Мотивация

**Проблема**: при каждом обращении оператора к списку заказов MES API делает полный запрос к БД. Когда несколько операторов одновременно обновляют страницу в поиске новых заказов для взятия в работу, БД получает повторяющиеся идентичные запросы. Единственный инстанс PostgreSQL не справляется с ростом нагрузки.

**Что планируем кешировать**: результаты запроса "список заказов по статусу X, страница N" - то есть ответы MES API на GET /orders?status=X&page=N. Эти запросы идентичны для всех операторов, данные редко меняются, и их повторное вычисление дорого.

**Что кешировать не будем**: детали конкретного заказа (GET /orders/{id}) - их запрашивают реже, а при изменении статуса нужна немедленная актуальность.

**Что это даст:**
- Снижение нагрузки на MES DB: большинство запросов к списку заказов будут обрабатываться из кеша, без обращения к БД.
- Снижение времени отклика: чтение из Redis занимает миллисекунды против десятков миллисекунд для запроса к PostgreSQL.
- Масштабируемость: при дальнейшем росте числа операторов и заказов нагрузка на БД будет расти медленнее.
- Стабильность: меньше конкурирующих запросов к единственному инстансу БД снижает риск деградации под пиковой нагрузкой.

## Предлагаемое решение

### Тип кеширования: серверное

Выбираем серверное кеширование - Redis на стороне MES API - а не клиентское (HTTP Cache-Control / ETag на стороне браузера).

**Почему не клиентское:**
Браузерный кеш работает per-client: каждый оператор кеширует данные у себя в браузере. Это не решает проблему нагрузки на БД - при N операторах DB всё равно получит N запросов при первой загрузке у каждого. Кроме того, когда один оператор берёт заказ в работу, браузерный кеш других операторов не инвалидируется - они видят устаревший список. Два оператора могут попытаться взять один и тот же заказ одновременно.

Серверный кеш разделяется между всеми операторами: если один уже запросил список заказов, все остальные получат результат из кеша. Инвалидация происходит centrally - при изменении статуса заказа кеш удаляется одним действием для всех.

### Паттерн: Cache-Aside

Используем паттерн **Cache-Aside** (ленивое заполнение кеша).

**Как работает:**
1. MES API получает запрос GET /orders?status=X&page=N.
2. Проверяет наличие ключа `orders:status:{X}:page:{N}` в Redis.
3. Если ключ есть (cache hit) - возвращает данные из кеша напрямую.
4. Если ключа нет (cache miss) - делает запрос к MES DB, сохраняет результат в Redis с TTL=60s, возвращает данные клиенту.

**Почему не Write-Through:**
Write-Through обновляет кеш при каждой записи: при изменении статуса заказа MES API должен сразу записать обновлённый список в Redis. Это требует вычисления обновлённого списка на каждую запись, увеличивает latency операции записи и добавляет сложность: нужно знать, какие именно ключи кеша затронуты. При этом статус меняется намного реже, чем читается список - кешировать каждую запись избыточно.

**Почему не Refresh-Ahead:**
Refresh-Ahead проактивно обновляет кеш до истечения TTL. Требует предсказания паттернов доступа: какие страницы и статусы будут запрошены в ближайшее время. У нас нет чёткой предсказуемости - операторы смотрят разные статусы в разное время. Refresh-Ahead создаёт дополнительные запросы к БД для обновления записей, которые могут никогда не понадобиться.

Cache-Aside лучше в нашем случае: кеш заполняется только для реально запрошенных комбинаций статус+страница, операция записи не усложняется, реализация проста и понятна команде.

### Стратегия инвалидации кеша

Используем **комбинацию программной инвалидации (по ключу) и TTL-страховки**.

**Программная инвалидация** - основной механизм:
Когда оператор меняет статус заказа (например, SUBMITTED -> MANUFACTURING_STARTED), MES API сразу после успешной записи в БД удаляет все ключи кеша, связанные с затронутыми статусами:
- `DEL orders:status:SUBMITTED:*` - список заказов со старым статусом изменился.
- `DEL orders:status:MANUFACTURING_STARTED:*` - список заказов с новым статусом изменился.

Инвалидация происходит немедленно - следующий запрос от любого оператора получит свежие данные из БД.

**TTL=60 секунд** - страховочный механизм:
Даже если программная инвалидация по какой-то причине не сработала (сетевой сбой при записи в Redis, баг в коде), кеш устареет максимум через 60 секунд. Для нашего сценария 60 секунд - приемлемое значение: операторы могут видеть незначительно устаревший список, но не потеряют заказ насовсем - следующее обновление даст актуальные данные.

**Сравнение стратегий инвалидации:**

- Временная (только TTL)
  - Плюсы: простая реализация, нет дополнительной логики на запись
  - Минусы: операторы видят устаревшие данные до истечения TTL (до 60 секунд). При конкуренции за заказы - неприемлемо: два оператора могут взять один заказ
  - Вывод: не подходит как основная стратегия

- Программная (по ключу) при каждом изменении статуса
  - Плюсы: данные всегда актуальны после изменения, операторы сразу видят свежий список
  - Минусы: нужно явно инвалидировать нужные ключи при каждой записи; если инвалидация упала - кеш устарел бессрочно
  - Вывод: подходит, но нужна TTL-страховка на случай сбоя

- Комбинация: программная + TTL (выбранная стратегия)
  - Плюсы: немедленная актуальность при штатной работе; TTL как страховка от бессрочного устаревания при сбое инвалидации
  - Минусы: чуть сложнее реализации - нужно удалять ключи по паттерну
  - Вывод: оптимальный вариант для нашего сценария

- Инвалидация по событию (message bus)
  - Плюсы: можно разделить логику инвалидации и бизнес-логику
  - Минусы: избыточная сложность для текущего масштаба; RabbitMQ уже используется для передачи заказов между системами - добавлять туда события инвалидации кеша внутри MES API нецелесообразно
  - Вывод: не подходит на текущем масштабе

### Технология

**Redis** - стандартный выбор для серверного кеша:
- Команды GET/SET/DEL атомарны - нет race condition при одновременных запросах нескольких операторов.
- Поддержка TTL из коробки - не нужна дополнительная логика устаревания.
- Поддержка паттернов при удалении ключей (`KEYS orders:status:SUBMITTED:*` + `DEL`) для массовой инвалидации.
- Managed Redis доступен в Yandex Cloud - операционная нагрузка на DevOps минимальна.

Для Java (MES API написан на C#, но CRM и Shop - на Java) интеграция через Lettuce или Jedis. Для MES API (C#) - через `StackExchange.Redis`.

## Дополнительное задание. Сравнение решений

В нашем случае есть два реалистичных варианта:

| | Решение 1: Redis Cache-Aside на MES API (рекомендуемое) | Решение 2: HTTP-кеширование (ETag + Cache-Control) |
|--|--|--|
| Описание | MES API кеширует результаты запросов к БД в Redis. Все операторы читают из общего кеша. При изменении статуса - программная инвалидация. | MES API возвращает ETag (хеш ответа) и Cache-Control: max-age=30. Браузер или промежуточный HTTP-кеш (nginx) кеширует ответы. |
| Плюсы | Нагрузка на БД снижается для всех операторов одновременно. Инвалидация работает для всех сразу. Кеш разделяется: N операторов делают 1 запрос к БД вместо N. Гибкий контроль TTL и ключей. | Не требует дополнительного сервиса (Redis). Реализуется на уровне HTTP-заголовков. Работает автоматически через браузерный кеш и nginx. |
| Минусы | Требует добавления Redis как нового сервиса (операционная нагрузка, +1 компонент для DevOps). Нужна явная логика инвалидации в коде MES API. | Кеш per-operator: каждый браузер кеширует независимо. При N операторах DB всё равно получит N запросов при первой загрузке. Инвалидация не работает немедленно между операторами: браузер другого оператора не узнает, что один оператор взял заказ. Риск конкуренции за один заказ. |

**Заключение:** Решение 1 (Redis Cache-Aside) решает проблему принципиально: снижает нагрузку на БД пропорционально числу операторов и обеспечивает согласованность данных между ними. Решение 2 снижает нагрузку только при повторных запросах одного и того же оператора, но не решает главную проблему - конкурентные запросы нескольких операторов к БД. Кроме того, HTTP-кеш создаёт риск, что двое операторов возьмут один заказ из-за устаревших данных в разных браузерах. Redis Cache-Aside при наличии managed-сервиса в Yandex Cloud добавляет минимальную операционную нагрузку и является правильным решением.
